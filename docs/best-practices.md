# 业界最佳实践：应用层 ECDHE 密钥协商（小程序 <-> SpringBoot，请求明文、响应加密）
> 前提：**应用层加密是 HTTPS 的叠加防护，绝不替代 HTTPS**；目标：抵御「用户手机被植入恶意根证书导致TLS被MITM」的场景；保留前向保密PFS，控制握手开销。
> 定位：**TLS负责传输层安全；应用层ECDHE负责业务响应数据加密**。

整体范式参考：OAuth / OIDC、Signal、Web Crypto、API应用层加密的成熟设计，不是自己从零造密码协议。

## 一、整体架构（业界标准）
分层：
1. **传输层：强制HTTPS**，域名备案+小程序业务域名配置，TLS 1.2+，禁用弱加密套件；证书使用正规CA证书。
2. **应用层：ECDHE + ECDSA签名（防MITM）+ HKDF密钥派生 + AES-GCM加密响应**
    - 服务端持有**长期静态ECDSA密钥对**（只用来签名每次ECDHE临时公钥，**不参与密钥协商**）
    - 每次握手双方各生成一次性X25519临时密钥对（ECDHE）
    - 服务端临时公钥，必须用服务端静态ECDSA私钥签名；小程序端用服务端静态ECDSA公钥校验签名（核心，抵御裸ECDHE中间人攻击）
    - 共享秘密通过HKDF派生AES-GCM密钥，不要直接把ECDH共享秘密当AES密钥
3. **会话模型：一次握手，会话密钥复用一段时间（核心优化，避免每次请求两次HTTP）**
    - 会话绑定 `sessionId`，后端Redis存储：`sessionId → AES密钥、创建时间、过期时间`，设置TTL（推荐5分钟，可根据业务调整）
    - 小程序：**内存缓存sessionId、AES密钥；禁止持久化到storage/localStorage**；页面销毁、小程序切后台主动丢弃密钥。

> 安全能力：具备 **PFS前向保密**。就算未来服务端静态ECDSA私钥泄露，过去抓包的历史密文依然无法解密。

## 二、完整标准流程（业界最佳实践）
### 1. 部署阶段（一次性）
1. 服务端生成长期 **ECDSA P-256密钥对**
    - ECDSA私钥：服务端保管，不能下发
    - ECDSA公钥：**内置到小程序代码中**（公钥不怕泄露）
> 这个公钥是根信任锚点，用来校验每次握手时服务端临时X25519公钥的签名，是抵御应用层MITM的根基。

### 2. 握手接口 `/api/ecdhe/handshake`（明文HTTPS，按需调用，不是每次业务都调用）
> 只有小程序本地没有有效session时才发起握手。
1. 小程序生成**一次性X25519密钥对**，将客户端临时公钥明文发给后端。
2. 后端生成**一次性X25519密钥对**。
3. 后端计算ECDH共享秘密：`后端临时私钥 + 客户端临时公钥`。
4. 后端使用**静态ECDSA私钥**，对本次服务端X25519临时公钥做签名。
5. HKDF 派生AES-GCM密钥（传入共享秘密 + 固定salt + info字段，标准化派生）。
6. 创建唯一`sessionId`，Redis写入会话，设置TTL。
7. 返回：`sessionId`、服务端临时X25519公钥、ECDSA签名。
8. 小程序校验：使用内置的服务端静态ECDSA公钥校验签名。签名失败 → 直接丢弃，中断流程（中间人篡改公钥会在这里被拦截）。
9. 校验通过：小程序计算ECDH共享秘密，使用相同HKDF参数得到一致AES密钥；内存保存sessionId、AES密钥；客户端X25519临时密钥对可以丢弃。

> ✅ 关键点：**签名对象是服务端临时公钥**，防止中间人替换ECDHE公钥。这是裸ECDHE和安全ECDHE协议最大区别。

### 3. 业务接口（多次复用会话，请求明文，响应加密）
1. 小程序发起业务请求：**请求体明文JSON**，HTTP请求头带上 `X-Session-Id: sessionId`。
2. SpringBoot服务端：
    - 读取明文请求，执行业务逻辑，得到VO。
    - 通过`X-Session-Id`从Redis取出AES密钥；session不存在/过期返回固定错误码 `SESSION_EXPIRED`。
    - `@EncryptResponse`触发ResponseBodyAdvice：
        - Jackson序列化VO为明文JSON
        - AES-GCM加密：每次加密生成全新12字节nonce，输出 nonce、ciphertext、tag
        - 返回标准密文结构体
      ```json
      {
        "nonce":"base64",
        "cipherText":"base64",
        "tag":"base64"
      }
      ```
3. 小程序收到响应：
    - 解析密文结构，AES-GCM解密（tag校验失败直接丢弃，防篡改）
    - 拿到明文JSON，反序列化；AES密钥继续保存在内存，供后续接口复用。

### 4. 会话过期处理 & 自动重握手（前端逻辑）
1. 小程序调用业务接口，如果收到后端返回 `SESSION_EXPIRED`：
    - 丢弃本地旧session和AES密钥
    - 自动发起ECDHE握手，拿到新session
    - 自动重试当前业务请求（有限重试次数，防止死循环）
2. 优化：**会话预续约**，会话剩余TTL不足60秒时，小程序在空闲时机发起轻量续约接口，只刷新Redis TTL，**不重新跑ECDHE**。续约接口开销极低。

## 三、前端（小程序）并发保护最佳实践（非常容易踩坑）
小程序页面并发调用多个业务接口，同时session失效，会并发触发多次握手请求。
✅ 业界标准方案：**握手状态锁**
- 全局变量标记 `isHandshaking`。
- 如果正在握手，新的业务请求进入等待队列，等待握手完成后统一执行；
- 避免同时发起多个重复握手请求，浪费资源。

## 四、密码学参数（标准化，不要自己乱选）
|项目|推荐选型|说明|
|---|---|---|
|ECDHE临时密钥|X25519|速度快、安全，Web Crypto支持|
|服务端长期签名密钥|ECDSA P-256|用于签名临时公钥，抗中间人|
|密钥派生|HKDF-SHA256|绝对不要直接使用ECDH共享秘密作为AES密钥|
|业务加密|AES-GCM 128|认证加密，同时加密+完整性校验；12字节nonce每次必须全新随机|
|填充/哈希|遵循标准，不要自定义|不使用自研哈希、加盐方案|

> 不要自己发明密码协议，全部使用NIST推荐标准。

## 五、后端工程最佳实践（SpringBoot）
1. 会话存储：Redis，key设置TTL，自动清理过期会话；单机可用Caffeine缓存，分布式必选Redis。
2. `@EncryptResponse`注解：方法级别开关，灵活控制哪些接口返回加密响应；ResponseBodyAdvice统一处理。
3. 错误码标准化：
    - `SESSION_EXPIRED`：会话不存在/过期，前端触发重握手
    - `DECRYPT_FAILED`：密文篡改、tag校验失败
4. 安全日志：不要打印AES密钥、明文敏感数据；日志只记录sessionId、错误类型。
5. 限流：握手接口增加限流，防止攻击者疯狂请求握手消耗服务器CPU。ECDHE签名/验签CPU开销高于普通接口。

## 六、安全边界与取舍（业界一定会评估）
### ✅ 这套方案带来的防护
即使TLS被中间人解密（手机安装恶意根证书）：
1. 请求参数：**仍然是明文**，中间人可以看到请求内容；
2. 响应数据：应用层AES-GCM密文；中间人没有AES密钥，无法解密，也无法篡改。
> 如果请求参数也敏感，需要改成**请求也加密**。

### ✅ 安全特性
- ✅ 前向保密PFS
- ✅ 防中间人篡改ECDHE公钥（ECDSA签名校验）
- ✅ 响应防篡改（AES-GCM tag）
- ✅ 会话密钥不落盘（小程序内存）

## 七、可选增强（高安全业务才加）
1. 请求增加 `X-Request-Nonce` + 请求签名：防止重放攻击（当前需求请求明文场景可选）
2. 服务端静态ECDSA公钥轮换机制，小程序支持公钥热更新，避免小程序发版才能更新公钥。
3. 会话强制失效：用户登出，后端直接删除Redis会话。

## 八、对比替代方案选型参考（业界怎么选）
1. **ECDHE+ECDSA签名 + 会话复用（当前方案）【推荐，高安全】**
    - 优点：PFS，握手次数少；一次握手复用多次业务请求；密码运算少。
    - 缺点：需要会话管理；前端需要实现握手锁、自动重握手逻辑。
2. **RSA-OAEP（客户端生成AES密钥，放入请求头）【简单，低安全】**
    - 优点：无需会话、无需握手接口；实现简单。
    - 缺点：**无PFS**；每次请求RSA加解密，高并发CPU压力大。适合低QPS、无PFS要求场景。

## 九、避坑清单（业界常见踩坑点）
1. ❌ 裸ECDHE（不对服务端临时公钥做ECDSA签名）→ 中间人可以替换双方ECDHE公钥，应用层MITM。
2. ❌ ECDH原始共享密钥直接当AES密钥，不使用HKDF派生。
3. ❌ AES-GCM nonce复用（同一个密钥+相同nonce会直接泄露密钥）。
4. ❌ 小程序把AES密钥持久化存储到本地storage。
5. ❌ 每次业务请求都执行完整ECDHE握手（性能灾难）。
6. ❌ 应用层加密替代HTTPS。

## 一句话总结业界最佳实践
> **传输层HTTPS打底；应用层使用带ECDSA签名校验的X25519 ECDHE做密钥协商，握手会话密钥复用一段时间；HKDF派生AES-GCM密钥加密响应；前端内存保存密钥、带握手锁和自动重握手逻辑；后端Redis管理会话，握手接口限流。**
> 这套是很多金融、政企小程序应用层加密的标准落地范式。

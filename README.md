**核心结论是：绝对禁止在客户端硬编码或通过网络明文传输对称密钥，必须采用“混合加密”模式，即利用非对称算法（如RSA/ECDH）在TLS握手层之上安全协商出临时的对称密钥（如AES），实现“一次一密”。**

针对手机号字段加密场景，推荐以下三种主流密钥共享方案：

### 方案一：RSA 密钥封装（Key Encapsulation）—— 最易落地
这是最直观的方案，适合已有 RSA 证书体系的团队快速接入。
**交互流程：**
1. **服务端预置**：服务端生成 RSA 公私钥对，私钥严格保管（建议存入 KMS/HSM），公钥随 App 发布（硬编码在客户端或通过接口动态下发）。
2. **客户端生成会话密钥**：每次请求前，客户端随机生成一个对称密钥（如 AES-256 密钥）。
3. **加密对称密钥**：客户端用服务端的 RSA **公钥**加密这个 AES 密钥。
4. **发送报文**：客户端将「RSA 加密后的 AES 密钥」+「AES 加密后的手机号密文」一起发给服务端。
5. **服务端解密**：服务端用 RSA **私钥**解密拿到 AES 密钥，再用 AES 密钥解密手机号。

**优点**：实现简单，不需要复杂的密钥协商协议。
**缺点**：每次请求都要做一次 RSA 解密，服务端有一定性能开销；且不具备前向保密性（如果 RSA 私钥泄露，历史所有抓包数据都能被解密）。

---

### 方案二：ECDH 密钥协商（Key Agreement）—— 推荐方案
这是目前业界更推荐的做法，TLS 1.3 也强制使用 ECDHE。
**交互流程：**
1. **服务端预置**：服务端生成 ECDH 公私钥对（如使用 P-256 或 X25519 曲线），私钥严格保管，公钥随 App 发布或动态下发。
2. **客户端生成临时密钥对**：每次请求前，客户端生成一个临时的 ECDH 公私钥对（ephemeral key pair）。
3. **交换公钥**：客户端将自己的临时公钥发给服务端（可放在请求头中）。
4. **各自计算共享密钥**：
    - 客户端用「自己的临时私钥 + 服务端公钥」计算出共享密钥
    - 服务端用「自己的私钥 + 客户端临时公钥」计算出相同的共享密钥
5. **派生对称密钥**：双方对共享密钥做 KDF（如 HKDF-SHA256）派生出 AES 密钥。
6. **加密传输**：客户端用派生的 AES 密钥加密手机号，连同客户端临时公钥一起发给服务端。

**优点**：具备前向保密性（每次请求用不同的临时密钥，即使服务端私钥泄露，历史数据也无法回溯解密）；ECDH 计算效率高于 RSA。
**缺点**：实现复杂度略高于 RSA 方案，需要处理密钥序列化、KDF 派生等细节。

---

### 方案三：KDC 密钥分发中心 —— 适合大规模多端场景
如果你们有多个客户端类型（iOS、Android、Web、小程序）且需要集中管理密钥，可以考虑引入 KDC。
**交互流程：**
1. 每个客户端在注册/登录时，与 KDC 预共享一个长期主密钥（KEK）。
2. 当需要加密通信时，客户端向 KDC 申请一个临时会话密钥。
3. KDC 用客户端的 KEK 加密会话密钥后返回给客户端。
4. 客户端用会话密钥加密手机号，服务端也从 KDC 获取同一会话密钥进行解密。

**优点**：密钥集中管理，便于轮换和审计。
**缺点**：架构复杂，需要额外部署 KDC 服务；对于单纯的手机号字段加密场景来说，可能过度设计。

---

### 针对你们场景的推荐方案

结合你们的需求（App 手机号字段加密、合规整改、尽快落地），我建议采用 **方案二（ECDH）的简化版**：

#### 推荐架构：ECDH + AES-GCM + KMS
```
┌─────────────┐                          ┌─────────────┐
│   客户端     │                          │   服务端     │
│             │   1. 获取服务端公钥       │             │
│             │◄─────────────────────────│  公钥(KMS)  │
│             │                          │             │
│  2. 生成临时ECDH密钥对  │                          │             │
│             │   3. 计算共享密钥+KDF    │             │
│             │                          │  4. 计算共享密钥+KDF  │
│             │   5. AES-GCM加密手机号   │             │
│             │   + 客户端临时公钥       │             │
│             │─────────────────────────►│             │
│             │                          │  6. AES-GCM解密手机号  │
└─────────────┘                          └─────────────┘
```

**关键实现要点：**
- **对称算法**：AES-256-GCM（带认证，防篡改）
- **密钥协商**：ECDH（P-256 或 X25519 曲线）
- **密钥派生**：HKDF-SHA256
- **服务端私钥存储**：接入云厂商 KMS（阿里云 KMS / 腾讯云 KMS 等），不要硬编码在代码里
- **客户端公钥获取**：建议通过接口动态下发（而非硬编码在 App 包里），便于密钥轮换
- **每次请求生成新的临时密钥对**：实现前向保密

---

### 需要避开的坑

| 错误做法 | 风险 |
|---------|------|
| 对称密钥硬编码在客户端代码中 | 反编译即可拿到密钥，形同虚设 |
| 对称密钥通过明文接口下发 | 抓包直接拿到密钥 |
| 用 Base64 / URL 编码当加密 | 不算加密，监管不认可 |
| 所有请求共用同一个对称密钥 | 密钥泄露后所有历史数据暴露 |
| RSA 公钥硬编码且永不轮换 | 一旦私钥泄露，无法补救 |
| ECDH 共享密钥直接当 AES 密钥用 | 缺少 KDF 派生，密钥质量不可控 |

---

### 落地建议

1. **先做 POC**：选 1-2 个高风险接口（如登录、绑定手机号），用 ECDH+AES 方案验证可行性。
2. **服务端优先接入 KMS**：密钥管理是合规检查的重点项，硬编码密钥在审计时会被挑战。
3. **客户端做好密钥缓存**：服务端公钥可以缓存，避免每次请求都拉取；但客户端临时密钥对必须每次新生成。
4. **日志脱敏同步推进**：即使接口加密了，如果服务端日志打印了明文手机号，风险依然存在。
